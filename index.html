Step 01 — The Job

Choose the loot.

Every item has a weight and a value. The bag can only hold so much. Edit the haul, set the capacity, then lock it in — every algorithm below runs on exactly this input.

ItemWeightValue

Capped at 6 items so the blueprints below stay readable — the algorithms themselves scale to any n.

The brief

  • Given n items, each with weight w and value v, and a bag of capacity W — pick a subset that maximises total value without exceeding W.
  • Each item is taken whole or not at all — no cutting the painting in half. That's what makes it 0/1.
  • Three strategies, same job: check everything, remember what you've computed, or reason about what's even worth checking.
  • This is the classic combinatorial-optimisation testbed for comparing exhaustive search, dynamic programming, and intelligent pruning — straight out of Units 4 & 5 of the DAA syllabus.
Strategy 01

Brute Force

For every item, try both branches — take it, or don't. Recurse until every item has a decision, then compare all resulting bags. Correct, exhaustive, and it never gets smaller than it has to be.

▸ Pseudocode 
function solve(i, remaining):
  if i == n or remaining == 0:
    return 0
  // item i does not fit — only one branch
  if weight[i] > remaining:
    return solve(i+1, remaining)
  // branch: leave it, or take it
  leave = solve(i+1, remaining)
  take  = value[i] + solve(i+1, remaining - weight[i])
  return max(leave, take)
Strategy 02

Dynamic Programming

Same recursion as Brute Force is hiding inside — but it keeps asking the same sub-question ("best value using the first i items with w capacity left?") over and over. DP just answers each one once, bottom-up, and looks it up forever after.

▸ Pseudocode 
for i from 1 to n:
  for w from 0 to W:
    if weight[i] <= w:
      dp[i][w] = max(dp[i-1][w], value[i] + dp[i-1][w-weight[i]])
    else:
      dp[i][w] = dp[i-1][w]
// answer sits at dp[n][W]; walk it backwards to recover the chosen items
Strategy 03

Branch & Bound

Explore the most promising branches first — ranked by a quick "best-case" estimate (what you'd get if you could slice the next item fractionally). The moment a branch's ceiling can't beat the best bag found so far, cut it. No table, no wasted recursion.

function bound(node):
  // best case: fill remaining capacity greedily by value/weight ratio,
  // allowing the last item to be sliced fractionally
  return node.value + fractionalFill(remaining items, remaining capacity)

queue = [root]           // ordered by bound, highest first
best = 0
while queue not empty:
  node = queue.popHighestBound()
  if node.bound <= best: continue        // prune
  if node.isLeaf: best = max(best, node.value); continue
  for child in [include next item, exclude next item]:
    if child.bound > best: queue.push(child)
    else: mark child pruned

Step 06 — Complexity Analysis

So which one do you actually hire?

Node counts are satisfying, but the real answer is asymptotic. Here's how the three strategies stack up on paper.

StrategyTime complexitySpace complexityWhat it actually explores
Brute Force O(2ⁿ) O(n) recursion depth Every possible subset, no matter how the weights fall. No memory of repeated work.
Dynamic Programming O(n·W) O(n·W), reducible to O(W) Pseudo-polynomial — fast when capacity W is modest, but the table itself grows with W, not just n.
Branch & Bound O(2ⁿ) worst case O(2ⁿ) worst case, usually far less Only the branches whose optimistic bound can still beat the best answer so far — in practice a sliver of the full tree.
Pick DP when

Capacity W is small-to-moderate and items are few enough that an n×W table fits comfortably in memory. Guarantees the optimum in predictable time — no surprises.

Pick Branch & Bound when

Capacity is huge (a DP table would be enormous) but the item values/weights are structured enough that a good bound prunes aggressively. Same worst case as brute force, usually nowhere near it in practice.

Pick Brute Force when

n is tiny, you need a ground-truth check to validate the other two, or you're teaching the recursion before optimising it away. Otherwise — never at scale.
